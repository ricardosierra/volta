    1. `apps/mobile/src/core/save/save_data.gd`:
    ```gdscript
    class_name SaveData
    extends RefCounted

    const CURRENT_SCHEMA_VERSION: int = 1
    ## Blocos gravados em profile.json. `settings` fica FORA — vai para settings.json
    ## (docs/architecture/save-system.md §2: settings nunca se perdem por corrupção de perfil).
    const PROFILE_BLOCKS: Array[String] = ["player", "progress", "stats", "records", "wallet", "inventory", "achievements", "challenges"]

    var meta: Dictionary = {"schema_version": CURRENT_SCHEMA_VERSION, "app_version": "0.1.0", "created_at": "", "updated_at": "", "device_id": ""}
    var settings: Dictionary = {}
    var player: Dictionary = {}
    var progress: Dictionary = {}
    var stats: Dictionary = {}
    var records: Dictionary = {}
    var wallet: Dictionary = {}
    var inventory: Dictionary = {}
    var achievements: Dictionary = {}
    var challenges: Dictionary = {}

    func to_dict() -> Dictionary:
        var out := {"meta": meta.duplicate(true)}
        for block in PROFILE_BLOCKS:
            out[block] = get(block).duplicate(true)
        return out

    func settings_to_dict() -> Dictionary:
        return {"meta": meta.duplicate(true), "settings": settings.duplicate(true)}

    func apply_settings_dict(data: Dictionary) -> void:
        settings = data.get("settings", {})

    static func from_dict(data: Dictionary) -> SaveData:
        var save := SaveData.new()
        save.meta = data.get("meta", save.meta)
        for block in PROFILE_BLOCKS:
            save.set(block, data.get(block, {}))
        return save
    ```
       Nota sobre "campo desconhecido preservado": como cada bloco já é um `Dictionary`
       genérico (não uma lista fixa de propriedades tipadas), qualquer chave extra dentro de
       um bloco (ex.: `player["campo_novo"]`) já sobrevive naturalmente ao round-trip — não
       precisa de um `_unknown` separado. Onde a preservação REALMENTE precisa de cuidado é
       em `meta`: se uma versão futura adicionar uma chave a `meta` que esta versão do app
       não conhece, `meta = data.get("meta", ...)` já preserva o dicionário inteiro como veio
       (não reconstrói campo a campo), então também está coberto. Documente esse raciocínio
       no SUMMARY em vez de adicionar complexidade desnecessária.

    2. `apps/mobile/src/core/save/file_save_service.gd` — implementação concreta.
       Estrutura obrigatória (nomes de método podem variar internamente, mas o comportamento
       abaixo é o contrato):
       - Construtor recebe `save_dir: String = "user://save/"` (parametrizável para os
         testes usarem um diretório isolado, ex.: `"user://test_save/"`, evitando conflito
         entre testes e com um save real de desenvolvimento).
       - `data: SaveData` mantido em memória; `_dirty: Dictionary` (Set de seções pendentes).
       - Primitivas **por arquivo** — usadas para `profile.json` E `settings.json` (mesma
         escrita atômica, mesma recuperação, arquivos independentes):
         - `_write_atomic(file_name: String, payload: Dictionary) -> void`: serializa com
           `JSON.stringify(payload, "  ")`, escreve em `<file_name>.tmp`, `flush()`, se
           `<file_name>` existir e for JSON válido copia para `<file_name>.bak`, depois
           `rename("<file_name>.tmp", "<file_name>")` via `DirAccess`.
         - `_load_with_recovery(file_name: String) -> Dictionary`: devolve
           `{"result": SaveResult, "data": Dictionary}` (`data` vazio quando `RECREATED`):
           a. `<file_name>` não existe → `RECREATED`.
           b. Lê; `JSON.parse_string()`; se `null` (inválido) → tenta `<file_name>.bak`.
              b1. `.bak` válido → usa os dados do backup, regrava o principal com eles,
                  `RESTORED_FROM_BACKUP`.
              b2. `.bak` também inválido/ausente → renomeia AMBOS para
                  `<file_name>.corrupt-<unix_timestamp>` e `<file_name>.bak.corrupt-<unix_timestamp>`
                  (nunca apaga), `RECREATED`.
           c. JSON válido → `OK`.
       - `save_profile(now)`: `_write_atomic("profile.json", data.to_dict())`; limpa `_dirty`.
       - `save_settings()`: `_write_atomic("settings.json", data.settings_to_dict())`.
       - `load_profile()`: `_load_with_recovery("profile.json")`; se `RECREATED`, `data =
         SaveData.new()` e grava; senão roda a cadeia de migrações (abaixo) sobre o
         `Dictionary` bruto → `SaveData.from_dict()`. Retorna o `result` da recuperação.
         **Não toca** `settings.json` nem o `data.settings` em memória.
       - `load_settings()`: `_load_with_recovery("settings.json")`; se `RECREATED`,
         `data.settings = {}` e grava; senão `data.apply_settings_dict(...)`. Sem cadeia de
         migração para settings nesta fase (a primeira migração real de settings, se vier,
         registra a própria cadeia — documente no SUMMARY).
       - Cadeia de migração: `var migrations: Array[SaveMigration] = []` (injetável via
         `register_migration(m: SaveMigration) -> void`, usado pelos testes para registrar a
         migração fake). Em `load_profile()`, depois de obter o `Dictionary` bruto, repita:
         `while true: var v = data["meta"]["schema_version"]; var next = migrations.filter(func(m): return m.from_version() == v); if next.is_empty(): break; data = next[0].migrate(data); ` —
         nunca pula versão (usa sempre a migração cujo `from_version()` bate com a versão
         atual).
       - `mark_dirty(section)`: adiciona a `_dirty`; não escreve em disco imediatamente (a
         decisão de QUANDO chamar `save_profile(true)` — fim de partida, pause, timer de 60s —
         é do consumidor, não deste serviço; documente isso num comentário no topo do arquivo
         em vez de implementar um `Timer`/hook de `NOTIFICATION_APPLICATION_PAUSED` aqui,
         porque isso requer um `Node` vivo na árvore de cena, que só existe a partir do
         Plano 01-10).
